# BookedRadar recovery writer-fence audit

Date: October 12, 2026  
Repository: `allenrandy74-dev/Bookedradar-platform-`  
Audited source: `d98107265a4674feebef3f6a0f84a8c172652647`  
Existing working-lab baseline supplied for this review: `3f4430c5ce942ea00cfe8d47aa1203444f0925d9`

## Verdict

**Cooperative application fencing is present; universal database writer fencing is not.** Ordinary PostgreSQL recovery mutations, composed intake workflows, normal retention, and the bounded synthetic SMS cleanup acquire the exact tenant lock:

`pg_advisory_xact_lock(hashtext('br_recovery'), hashtext(tenantId))`

Those paths hold it until the transaction commits or rolls back. The source importer uses the same lock and connection through its source reads and portal commit. However, manifest import, schema maintenance, the transactional restore drill, test/fixture SQL, and arbitrary privileged SQL do not all participate. Live freshness therefore depends on excluding those writers, not merely enabling the importer. A visibility lease or quarantine mechanism does not close this separate writer-fence gap.

This is a **static exact-source audit**, not a deployment, database, credentials, grants, traffic, or active-session inspection. No customer records, Render, Wix, or database were accessed. No application source was edited or published, and no tests or migrations were executed. The working lab was not changed. Changes being prepared after this commit, including imported-only visibility, audited quarantine/restoration and a proposed DB-clock lease, are outside this audit and must be reviewed at their own final commit.

## Scope and evidence

GitHub compare confirmed the audited head is one commit ahead of the supplied baseline, changing ten customer-portal importer/documentation/test files only. Existing recovery source, scripts, and source DDL are unchanged. The review downloaded exact-head reference copies and checked 198 file contents against Git blob identities: all matched.

Coverage included all tracked non-test JavaScript/MJS/shell source under `src/`, `scripts/`, `twilio/`, applicable repository-root backend files, source DDL, all `test/postgres-*` files, selected other source-ingestion/concurrency/fixture tests, the importer/reader/portal store, and relevant maintenance documentation. Static searches covered concrete recovery table names, the dynamic recovery table map, SQL mutation/DDL strings, transaction/lock boundaries, import/restore callers, and retention. The tracked tree has no repository `.agents/skills` or `AGENTS.md` entry. Archived ZIPs, unrelated downloaded assets, untracked operator scripts, external jobs and deployed database objects were not exhaustively inspected. Those cannot be assumed safe from this review.

### Retention consequence

The normal pruner is fenced, but it does not preserve every opportunity's originating receipt. The generic prune loop retains events by age, drops keys for removed events, and removes only terminal old actions; it does not delete the corresponding opportunity/contact/attribution. The PostgreSQL wrapper additionally retains recent reconciliation audit events. [src/recovery/store.js:395–436](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/recovery/store.js#L395-L436), [src/postgres-recovery-store.js:163–172](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-recovery-store.js#L163-L172)

A pruned originating receipt is **deterministic eligibility loss**: the source reader rejects it with `source_event_missing` rather than substituting opportunity creation/update time. [customer-portal/server/source-reader.mjs:88–99](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-reader.mjs#L88-L99) At this audited commit, failure leaves an existing portal projection unchanged; this is documented in [customer-portal/SOURCE_INGESTION.md:35–45](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/SOURCE_INGESTION.md#L35-L45). Therefore activation requires explicit withdrawal/retention enforcement. A subsequent quarantine/lease candidate may address this, but its behavior and tests must be verified independently; this report does not claim that future candidate permanently retains ineligible visibility.

## 2. Unfenced or differently fenced maintenance and alternate paths

### A. `importMigrationManifest`: definite source-writing bypass

`src/postgres-runtime.js` opens an ordinary transaction by default but acquires **no recovery advisory lock**. It directly upserts:

- Contacts: lines 173–183
- Opportunities: lines 185–196
- Events: lines 198–211
- Actions: lines 231–250
- Attribution: lines 252–262
- Sequence reset: lines 212–218
- All event keys: unconditional global delete, then rebuild, lines 220–229

Evidence: [src/postgres-runtime.js:71–92](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-runtime.js#L71-L92), [src/postgres-runtime.js:173–262](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-runtime.js#L173-L262), [src/postgres-runtime.js:323–339](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-runtime.js#L323-L339).

These upserts also permit replacement of stored tenant ownership from the manifest, unlike the normal store's conflict guard. Auditing the manifest beforehand does not coordinate with concurrent recovery or import work. `manageTransaction:false` delegates transaction ownership entirely to the caller; the helper itself then provides neither a transaction nor a fence.

**Activation consequence:** exclude this importer from the active source database during serving/importing, or redesign and verify its locking before use. Locking only tenants named in a manifest would still be inadequate for its global event-key delete. Any future multi-tenant lock design must account for every affected current tenant and newly arriving tenants, not just the manifest's row list.

### C. Schema application: different lock, no mandatory recovery-writer enforcement

`applyPostgresSchema` uses the single-key session advisory lock `bookedradar_schema_migration`, then executes supplied SQL in its own transaction. This is not the two-key `br_recovery`/tenant lock; recovery writers and the source reader never acquire that schema lock. [src/postgres-runtime.js:36–64](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-runtime.js#L36-L64).

The reviewed DDL creates/changes source tables, sequence defaults, indexes and idempotency constraints. It contains no recovery-write trigger or mandatory stored-procedure permission boundary that enforces `br_recovery` on every source write. The recovery tables also do not have foreign keys that preserve originating receipts on behalf of portal imports. [db/postgres-schema.sql:67–158](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/db/postgres-schema.sql#L67-L158), [db/postgres-schema.sql:251–254](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/db/postgres-schema.sql#L251-L254). DDL's own PostgreSQL relation locks may block queries; that does not establish the cooperative freshness contract.

### D. Transactional restore drill: different lock and active schema changes

`runPostgresTransactionalRestoreDrill` holds `bookedradar_restore_drill`, reads the source, renames the source schema, executes new schema SQL, invokes `importMigrationManifest(..., manageTransaction:false)` on its connection, checks content and **rolls back**. It never obtains the tenant recovery lock. [src/postgres-restore-drill.js:41–81](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-restore-drill.js#L41-L81).

The rollback is an intended no-persistent-change property, not evidence this procedure can safely run beside live recovery/import transactions. Its plain `BEGIN` source export performs multiple statements without a tenant lock or explicit repeatable-read snapshot. Source activity can invalidate its consistency checks and maintenance still acquires disruptive DDL locks. The server also has an enabled-by-flag startup route to this drill. [server.js:231–238](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/server.js#L231-L238). Exclude it during active import/serving.

### E. Direct SQL, repairs, old deployments and external jobs

The reviewed source DDL does not force privileged manual `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, restore or schema operations to obtain the recovery lock. Existing ordinary code is cooperative; database ownership or write privileges can bypass it. Neither a matching timestamp nor a content fingerprint repairs this gap. Source reads are plain `SELECT`, so an unfenced writer can commit between source statements or after validation but before the portal commit. [customer-portal/server/source-reader.mjs:72–119](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-reader.mjs#L72-L119), [customer-portal/SOURCE_INGESTION.md:25–33](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/SOURCE_INGESTION.md#L25-L33).

Unreviewed repair scripts, historical deployments, logical restore tools, external SQL jobs, triggers and security-definer functions require inventory at the approved destination. Absence from this source tree is not proof of absence from a deployed database. A source-SELECT-only importer role limits that importer; it does not constrain other writers.

### G. Paths that are not PostgreSQL recovery writers

The JSON `RecoveryStore` persists file state rather than the PostgreSQL tables. PostgreSQL-to-JSON rollback reads the database in a repeatable-read/read-only transaction and writes filesystem snapshots; ordinary backup/export and content-comparison helpers are also not source-table mutations. These paths need separate freeze/rollback discipline if later fed back through manifest import, but their reads are not additional source writer bypasses. [src/postgres-json-rollback.js:79–125](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-json-rollback.js#L79-L125), [src/postgres-full-export.js:6–43](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-full-export.js#L6-L43), [docs/postgres-state-adapter.md:147–151](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/docs/postgres-state-adapter.md#L147-L151).

Call-state/history, leads, transfer/chat, billing, pilot-admission and ops stores write their own tables. Their other lock namespaces must not be counted as recovery fences. For example, pilot admission reads recovery for safety but writes `voice_calls`; `postgres-aux-stores` writes only chat/transfer/metrics. [src/proof-pilot-admission.js:127–169](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/proof-pilot-admission.js#L127-L169), [src/postgres-aux-stores.js:7–27](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-aux-stores.js#L7-L27).

## 3. Importer boundary and lock-order/deadlock analysis

### Positive transaction proof at the reviewed source

The reader requires a top-level pool, explicitly starts `READ COMMITTED`, sets lock/statement/idle timeouts, then takes the exact recovery lock. Source statements execute only afterwards. It invokes the operation callback and performs the final `COMMIT` on the same connection; an uncertain commit is surfaced and not automatically retried. [customer-portal/server/source-reader.mjs:124–175](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-reader.mjs#L124-L175).

The importer callback reads source and performs all inquiry, source-link and service-audit writes on that connection. Its acquisition order is:

1. Tenant recovery advisory lock
2. Portal tenant row `FOR SHARE`
3. Plain source reads
4. Portal inquiry row `FOR UPDATE`
5. Portal source-link row `FOR UPDATE`
6. Portal mutations/audit, then top-level commit

Evidence: [customer-portal/server/source-importer.mjs:35–58](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-importer.mjs#L35-L58), [customer-portal/server/source-importer.mjs:74–105](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-importer.mjs#L74-L105). The portal workflow store also locks the inquiry before reading its current notes and mutating workflow state. It does not call back into recovery while holding that row in the reviewed implementation. [customer-portal/server/postgres-store.mjs:38–49](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/postgres-store.mjs#L38-L49), [customer-portal/server/postgres-store.mjs:105–170](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/postgres-store.mjs#L105-L170). Therefore no opposite portal-row→recovery-lock path was found among these reviewed ordinary paths.

### Hazards and required discipline

- **Future reverse-order integration:** a workflow that locks a portal inquiry/tenant row and then requests the recovery lock can deadlock with the importer. Keep recovery-before-portal order for every transaction touching both domains. Do not call an independently connected recovery store while retaining a portal lock.
- **Concrete unfenced migration/voice-workflow inversion:** manifest import writes call-control rows before recovery contacts. Voice intake writes recovery state before its final call-control update. With overlapping records, maintenance can hold call-state while waiting on a recovery row held by intake, while intake waits on that call-state row. This is a plausible static deadlock schedule, not an observed live incident. [src/postgres-runtime.js:117–124](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-runtime.js#L117-L124), [src/postgres-runtime.js:173–181](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-runtime.js#L173-L181), [src/postgres-intake-workflows.js:13–24](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-intake-workflows.js#L13-L24), [src/postgres-state-store.js:26–40](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-state-store.js#L26-L40). Simply adding the recovery lock late in migration, after row writes, would create another inversion; acquire a reviewed complete lock set before affected reads/writes or use verified maintenance exclusion.
- **Multi-tenant lock accumulation:** `cleanupFixtures` holds each acquired tenant lock until one final commit and iterates caller-provided map order. Current rehearsal builds its unique tenants in `a,b` order, but a reused/generalized helper with overlapping tenants in reversed order can deadlock. Future multi-tenant maintenance needs canonical lock ordering and bounded scope. Normal facade prune instead completes each tenant transaction separately. [scripts/lib/private-lab-sms-rehearsal-core.mjs:103–121](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/scripts/lib/private-lab-sms-rehearsal-core.mjs#L103-L121), [scripts/lib/private-lab-sms-rehearsal-core.mjs:136–140](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/scripts/lib/private-lab-sms-rehearsal-core.mjs#L136-L140), [src/postgres-server-stores.js:151–155](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/src/postgres-server-stores.js#L151-L155).
- **DDL/restore:** their different advisory locks serialize only participants using those same locks. DDL/relation locks can block normal reads/writes and form cycles with other row/relation locks. Do not treat lock timeout as authorization to run maintenance concurrently.
- **Long holding time:** importer portal lock waits occur while recovery is locked, serializing the whole tenant's ingestion, claim/completion and retention. Statement timeouts bound individual queries; idle timeout bounds idle time, not the complete multi-statement operation. JSON fallback lineage queries can scan much more than their result limit. Verify query plans, representative synthetic scale, end-to-end deadline and contention before activation. [customer-portal/server/source-reader.mjs:104–113](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-reader.mjs#L104-L113), [customer-portal/server/source-reader.mjs:133–160](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/server/source-reader.mjs#L133-L160).
- **Same destination/key semantics:** this is a database-local two-integer advisory key. A replica, different database, session lock in another namespace, changed tenant normalization or alternative key construction is not the same fence. Hash collisions can cause extra serialization; they do not justify skipping locks. Existing normal stores use plain `BEGIN`, so confirm supported session/default isolation and absence of pool wrappers that split statements across connections when validating the eventual runtime.
- **Failure semantics:** timeouts/deadlocks must abort the transaction and preserve old destination state; they must not bypass the lock or be recast as successful refreshes. An uncertain commit must be reconciled from durable state before retrying. No claim is made that legacy source writers have the newer importer's commit-uncertainty handling.

The checked integration source contains tests for post-wait visibility and retaining the fence through projection/audit commit. This audit inspected those tests but did not execute them; existence is not a fresh runtime pass. [customer-portal/test/source-ingestion.integration.mjs:200–219](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/test/source-ingestion.integration.mjs#L200-L219), [customer-portal/test/source-ingestion.integration.mjs:253–286](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/customer-portal/test/source-ingestion.integration.mjs#L253-L286).

## 4. Honest activation condition

**Status: not sufficient for live activation.** A defensible conditional statement is:

> At the reviewed commit, imports are fresh through their portal commit relative to concurrent source writers that acquire the exact same tenant recovery lock in the same PostgreSQL database and retain it through their writes' final commit. Maintenance and direct/alternate writers are outside that guarantee and must be excluded or brought under a separately reviewed enforced protocol.

Before any approved activation:

1. Pin and re-audit the actual final source/importer/visibility commits. Verify the running writer inventory, exact database/schema/tenant identity, connection handling and supported isolation; do not infer them from this code audit or from the lab's prior head.
2. Enumerate every application instance, worker, startup hook, scheduled job, console, migration/restore/repair tool, privileged role and database-side write mechanism with access to the source. Demonstrate that concurrent recovery writers cooperate, and operationally prevent unfenced access during imports/customer serving. Code review alone cannot prove that prevention.
3. Keep schema migration, manifest import, restore drill and test tools out of the active serving window. An approved maintenance window must stop new importer/refresh/serving work as appropriate, drain existing import/recovery/portal transactions, stop/drain all normal writers and old deployment instances, prevent independent jobs/console writes, perform only the separately approved maintenance, validate resulting source/schema/eligibility, then resume the pinned compatible writers and publisher. Merely setting a flag on one instance, disabling providers, seeing zero sessions once, or relying on an advisory lock no other process takes is insufficient. The existing maintenance guide itself requires independent-writer exclusion and drain verification. [docs/PRIVATE_LAB_MAINTENANCE.md:41–66](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/docs/PRIVATE_LAB_MAINTENANCE.md#L41-L66), [docs/PRIVATE_LAB_MAINTENANCE.md:111–133](https://github.com/allenrandy74-dev/Bookedradar-platform-/blob/d98107265a4674feebef3f6a0f84a8c172652647/docs/PRIVATE_LAB_MAINTENANCE.md#L111-L133).
4. If maintenance is intended to coexist with serving, first implement and independently test an enforced replacement protocol covering every changed source/eligibility field, multi-tenant/global operations and lock order. Do not silently promote the present manifest/restore utilities to concurrent writers.
5. Implement and verify explicit receipt-pruning/synthetic/malformed/missing-source withdrawal and restoration semantics. For the proposed next candidate, test quarantine/audit atomicity, imported-only visibility, the maximum DB-clock lease, fail-closed reads after expiry/refresh failure, and restoration only after fresh fenced eligibility checks. These are acceptance requirements, not findings that those changes already exist at this head.
6. Independently approve and verify tenant-restricted source access, minimum portal privileges and the portal tenant-row-lock privilege design; source read-only access alone is not tenant isolation. Verify that ordinary users cannot directly read source links/contact-bearing metadata or bypass the chosen visibility policy. No grants or credentials were inspected or changed here.
7. On an authorized disposable database, rerun cooperative writer/importer, prune/withdrawal, portal-edit, competing-import, timeout/deadlock, lost-commit and bounded-load tests against the final code. Include a deliberately unfenced writer demonstration or enforced-denial test so the boundary is explicit. Record actual results, rather than treating this static audit as a database test pass.

No action above is authorized or performed by this report. Source publication, runtime wiring, database changes, real-record access and customer activation remain separate approvals.
