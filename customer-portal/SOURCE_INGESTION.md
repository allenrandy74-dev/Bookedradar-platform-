## Internal API and trust boundary

`createPostgresSourceImporter({ pool, tenantId, sourceSchema, portalSchema, enabled: true })` binds one trusted server-selected tenant for the lifetime of the object. A tenant string is not authorization. The embedding system must verify the exact business and approved source/destination before constructing it; neither tenant nor schema may come from a browser request. Source and destination must be in the same PostgreSQL database, on the same connection/transaction. Default schemas are `bookedradar` and `bookedradar_portal`; only those and tightly formatted disposable-test schema names are accepted. The current synthetic staging schema is deliberately unsupported.

- `importInquiry({ opportunityId, expectedVersion })`: `null` means insert-only creation; a positive safe integer is required for refresh. It returns only `{ kind: 'create'|'refresh'|'unchanged', inquiryId, version }`. It accepts no detached snapshot, source timestamp/revision, fingerprint, contact data, tenant selector, or supplied service actor. Retry after an uncertain commit requires rereading durable state; no automatic mutation retry is implemented.
- `listOpportunityIds({ afterId: null, limit: 25 })`: returns `{ opportunityIds, nextAfterId }`. It selects only the bound tenant, uses keyset pagination, and accepts 1–25 IDs per page with one sentinel row. Listing is not an eligibility assertion or a complete/mutation-stable feed; each ID must be reread by the importer. Records inserted behind a prior cursor may need a later scan. No cursor is accepted as proof of freshness.
- `createPostgresRecoverySourceReader(...)` exposes the bounded list and internal `readInquiry({opportunityId})` for an approved diagnostic read. The latter returns the allowlisted source triple, mapped fields, binding and fingerprint; it is a server-only result, never a browser DTO. Its low-level `withFencedSource` callback is for trusted server composition by this importer. Returned data cannot be submitted to the importer for persistence.

## Consistent read and freshness boundary

Each operation starts a top-level `READ COMMITTED` transaction, sets 5-second lock / 10-second statement / 15-second idle-in-transaction timeouts, acquires the exact existing exclusive recovery tenant advisory lock, and only then queries source records. `READ COMMITTED` deliberately gets a fresh snapshot after any lock wait. Starting `REPEATABLE READ` before waiting could pin an older snapshot and is not used.

The same lock remains held through source validation, portal parent-row and binding locks, source-column compare-and-swap, dedicated audit insertion, and confirmed `COMMIT`. No network/source-provider call occurs inside the fence. Source queries are plain `SELECT`, not `FOR SHARE`/`FOR UPDATE`, so a future source role can remain SELECT-only. No source INSERT, UPDATE or DELETE is executed. Portal row locks are separate and necessary for workflow preservation.

This is a cooperative writer protocol grounded in the inspected store, not a universal database change detector. A migration, manual SQL writer, alternative store, replica, different database, or future source writer that does not take the exact advisory lock breaks the freshness proof. Before live use, review all writer paths and isolate such maintenance. The presence of the function or a configuration flag does not prove that operational contract. Source `updatedAt`, `occurredAt`, `source_sequence`, ingestion timestamps and the content fingerprint are explicitly **not** monotonic source revisions. Out-of-order detached refreshes cannot occur through this API because every import rereads current source inside its commit fence.

The lock temporarily serializes recovery work for that tenant. Statement timeouts cap individual queries, not the entire multi-query transaction. The direct-link JSON fallback predicates may scan more rows than they return; row/result bounds do not imply bounded scan cost. Query plans, indexes and contention need review with approved non-customer or suitably protected representative volume before activation. Lock/timeouts fail closed rather than skipping the fence.

## Bounded source and eligibility checks

For one tenant and opportunity ID, the reader selects at most one opportunity, its exact contact, and its exact originating event. SQL predicates always include the tenant even though source primary keys are global. It rejects SQL/payload tenant, ID and link conflicts. Only an absent legacy event owner can be supplied from the actual matching SQL tenant column; present empty/null/conflicting values fail. Receipt SQL time must agree with the validated payload receipt time. Missing/pruned receipts or contacts fail; opportunity creation/update time never substitutes for receipt time.

Fixed SQL JSON key allowlists drop arbitrary metadata, notes, transcripts, addresses, monetary/provider/consent fields before application materialization. Projected source JSON is capped at 32 KiB per row and then validated under the mapper's smaller field limits; malformed/null/oversized projections fail. Embedded receipt identity is read only to prove contact linkage; display values come from the current contact.

Additional direct-lineage reads select at most 101 related event rows, 101 action rows, and two attribution rows as overflow sentinels. More than 100 events/actions or one attribution fails without writes. These reads return only identity/link fields and explicit synthetic markers. They catch disagreement between the indexed opportunity link and JSON opportunity link using both predicates. Every selected record's SQL/payload link and ownership is checked, and a present contact link must resolve to the opportunity's exact bound contact (raw event keys follow the engine's namespace rule); legacy event/attribution absence may be established from the actual SQL owner, while a present conflict is rejected. An explicit Boolean true on the triple or any directly linked event/action/attribution, including `metadata.synthetic`, excludes the import; invalid marker types also fail.

This is a conservative direct-link check, **not proof that unmarked history is real**, not a complete inquiry inbox, and not a full historical lineage classifier. Contact-only outcome events, pruned records and indirect associations not explicitly linked by opportunity ID are outside its completeness claim. It produces no counts, revenue, recovery rate, booking claims or financial results.

If an existing imported row later becomes synthetic, malformed, missing or otherwise ineligible, a refresh fails and leaves the old projection unchanged. It does **not** quarantine, hide or delete that row. That retained visibility is an unresolved live-use blocker until an explicit eligibility/retention/withdrawal policy and its enforcement are approved and implemented.

## Durable destination and audit

The new migration only creates `source_links` and `source_ingestion_audit` in the separate portal schema; it does not modify existing source, portal or staging tables, create roles, or grant privileges. It is never applied automatically.

- `source_links` binds tenant/inquiry to source opportunity, contact key and originating event on first insert. Existing inquiries without a binding are not automatically adopted. A later contact or source-event relink is rejected even if the new triple is internally valid. The fingerprint is SHA-256 of allowlisted mapped fields and binding. First-imported and last-observed times record successful observations; unchanged imports update only the observation/fingerprint checkpoint, with no inquiry version/audit bump.
- The importer locks the portal parent before a separate fresh parent/notes read, so a note writer that just committed is seen consistently. It checks the expected version and uses version CAS for source changes. It inserts only into an absent inquiry, never upserts over human work.
- Only name, email, phone, subject, source and received time can refresh. Status, assignee, summary and all note rows remain untouched. Source recovery statuses never become human workflow states. The unchanged customer store continues rejecting source-column changes.
- The clock is read with `clock_timestamp()` **after** portal/binding lock waits; transaction-start time cannot incorrectly predate a just-committed human edit. Clock regression fails rather than manufacturing a newer timestamp.
- Separate service audits use fixed `recovery_importer_v1`, `inquiry.source_created` / `inquiry.source_refreshed`, changed field names, versions and time. They contain no name, phone, email, raw notes, contact key, receipt ID, payload or credential. Existing human audit schema/member actors are unchanged.
- Inquiry, binding and source audit are one transaction. Insert collision, stale version, audit failure, bad source or binding conflict rolls back. Connection/acquisition/driver/release failures use fixed sanitized labels; an uncertain commit poisons the connection and is not retried. No durable quarantine-error log is added.

## Proposed first-business read-only pilot scope, still unapproved

A later bounded proposal should name one verified business tenant, a finite opportunity/date scope, the selected customer viewer(s), the destination database/schema, and a retention period before accessing records. The existing synthetic lab must not silently become that destination.

1. **Fields displayed/stored:** current contact name, email, phone; current opportunity service type as subject; stored source label; original receipt time; opaque inquiry identity. No transcript, arbitrary summary/internal metadata, addresses, amounts, revenue, consent/opt-out state, action result, provider payload or credentials. Summary starts empty. Human workflow columns exist but the initial customer view can use viewer-only membership; no provider mutation is offered.
2. **Temporary validation reads:** scoped source opportunity/contact/receipt identities and types, receipt contact identity, SQL owner/link/time columns, and the explicit synthetic markers on the bounded direct lineage described above. No full source/export snapshot. Do not export the internal reader result or save it in logs.
3. **Restricted durable metadata:** tenant-scoped source bindings/fingerprint/observation times and the minimal separate service audit. The contact key may contain a phone/email under the real engine identity scheme, so this binding table is contact data and needs the same restricted access and retention review; it is not safe to expose as an audit DTO.
4. **Access:** separately reviewed internal service role with SELECT-only source access, minimal necessary portal reads/writes and lock permissions, no source write privileges or grants to customer browsers. Tables contain multiple tenants: SQL filtering is the library boundary, not database row-level authorization. A role/view/RLS design enforcing the approved tenant should be evaluated before credentials are provisioned. The portal tenant `SELECT ... FOR SHARE` additionally requires UPDATE privilege on at least one tenant column under PostgreSQL's row-lock permission rules; ordinary tenant SELECT alone is insufficient. Do not grant a security-sensitive tenant column merely to make this pass: review a constrained lock function/role design or equivalent authorization-preserving mechanism before activation. No grants, RLS or credential is created in this candidate. Secure credential handoff and any persistent-access change require their own authorization.
5. **Publisher and membership:** an explicitly reviewed bounded invocation/publisher and verified identity-to-tenant/viewer binding, exact HTTPS origin, protected sessions, and customer DTO allowlists. No new importer route, scheduler, batch runner, invitation or live UI publishing is included. Existing synthetic identity proof does not approve another business or customer membership.
6. **Release gates:** decide and implement eligibility, old-row hiding/quarantine and retention; verify every source writer uses the fence; approve destination/migration/rollback/least privilege; verify bounded publisher and customer access; run exact-head database/security/browser checks; obtain separate deployment/data-transfer/customer-access approval. Source-only publication, if later approved, would not satisfy these gates.
